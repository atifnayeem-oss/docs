Vapi tests run in Ringup's test mode, the same one every integration uses. The fixtures
live in one place, [Testing](/concepts/testing): the test card (`4111 1111 1111 1111`), the
decline card, and the test merchants you create in the dashboard. This page covers the Vapi
specifics for [call transfer](/integrations/vapi/call-transfer), the recommended integration.

## Rehearse on a test copy of your agent

When you add payment from the Ringup dashboard (see [Call
transfer](/integrations/vapi/call-transfer)), you wire a test copy of your agent in test mode,
with the tool and prompt line in place. Call it from your own phone: you hear your actual agent
take the order, the heads-up line, the transfer, and the full payment flow, before anything you
own changes.

Wiring by hand instead? Point the transfer tool's `server.url` at
`https://ringup.dev/api/transfer-destination` with your test key as `server.secret`, and call
your agent. Two journeys to run:

1. **First-time caller**: on your first call, the payment line texts a secure link; you pay
   with `4111 1111 1111 1111`, and the call announces the payment the moment it lands.
2. **Recognized caller**: call again from the same phone; you are greeted by name and pay on
   the saved Visa ending 1111 with one yes.

Both should end with a confirmation code read back and a test-mode `checkout.succeeded`.

## Verify the wiring after go-live

Read the assistant back from the Vapi API and check three things:

- Both tools are attached: `identify` and `transfer_to_payment` appear in the assistant's
  `toolIds`, and the transfer tool is `async: true` with the Ringup `server.url`.
- The prompt block is present (identify at the greeting; transfer on order confirmation).
- The agent's phone number can transfer to SIP: Vapi-native and SIP-trunk numbers can; a
  number imported from a telephony provider cannot (the guide's warning covers the options).

<Note>
Vapi's dashboard does not always render apiRequest tool names; the Vapi API is the source of
truth for wiring.
</Note>

## Reading test results

Only a `succeeded` charge result with a `charge_id` proves a payment happened; an agent can
narrate success it did not have. Always validate with a **voice call**, never text chat:
transfers only exist on voice, so a chat smoke test proves nothing.
