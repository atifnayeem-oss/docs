description: "Ringup posts a signed event to your server when a payment completes or fails, so your system can mark the order paid without waiting on the call."
---

Ringup posts an event to your server when a Checkout Session finishes, paid or not. Your system
learns the outcome out of band, without waiting on the call. It is the same across every platform,
so you write one handler.

## Register your endpoint

In the [dashboard](https://ringup.dev/dashboard/#/webhooks), open **Webhooks** and add your HTTPS
endpoint. Copy the signing secret from the confirmation: it is shown once and cannot be recovered
afterwards. Ringup then delivers every event below to it, signed. You can register more than one
endpoint, disable or delete one at any time, and each environment (Test and Live) keeps its own
list. The same page shows each endpoint's recent deliveries, with attempt counts and the last
error when one failed.

Prefer to script it? The API does the same thing, with your environment's key:

```bash
curl -X POST https://api.ringup.dev/v1/webhook_endpoints \
  -H "Authorization: Bearer rk_test_5f2a8c1d9e4b7a3f6c0d" \
  -H "Content-Type: application/json" \
  -d '{"url": "https://example.com/ringup/webhook"}'
```

The signing secret is in the response, shown once here too.

## The envelope

Every event has the same shape:

```jsonc
{
  "event_id": "evt_9f2",         // unique per event; use it to dedupe
  "type": "checkout.succeeded",  // see the catalog below
  "environment": "test",         // "test" or "live"
  "created_at": "2026-07-21T18:05:12Z",
  "data": { ... }                // shape depends on type
}
```

## Event catalog

| Type | When it fires |
|---|---|
| `checkout.succeeded` | A Checkout Session was paid, on a saved card or through the texted link. |
| `checkout.failed` | The charge was declined, or the session expired unpaid. |
| `checkout.step_up_required` | Screening found a risk signal on the caller's number, so their saved card was withheld and they were texted a link instead. |
| `merchant.connected` | A merchant finished connecting their payment processor to Ringup. |

The catalog is deliberately small. A first-time link payment is a `checkout.succeeded` like any
other, not a separate event.

## `checkout.succeeded`

The one you build against. Its `data` carries everything you need to mark an order paid:

```jsonc
"data": {
  "checkout_session_id": "cs_test_x9f2",
  "charge_id": "chg_5m1p",
  "status": "succeeded",
  "amount_cents": 1900,
  "currency": "USD",
  "processor_payment_id": "00467SVWM1EKC",   // the id in the merchant's own processor
  "merchant_id": "tonys-pizza",
  "order_id": "ord_7f21",              // your order id, echoed; null if you passed none
  "platform_call_id": "call_abc123",   // your platform's call id, to match back to the call
  "card": { "brand": "VISA", "last_four": "1111" },  // null when no card was involved
  "wallet": null,                      // "apple_pay" | "google_pay" when a wallet paid
  "metadata": { "table": "12" }        // your own key/value pairs, echoed
}
```

Match on the `order_id` you passed (or `platform_call_id`), store the `charge_id`, and flip your
order to paid.

A payment made with Apple Pay or Google Pay on the pay page arrives as this same event with
`wallet` naming the wallet and `card` null: a wallet payment saves no card, so there is no brand
or last four to report. Label it "Apple Pay" or "Google Pay" in your own surfaces rather than
treating the missing card as a gap.

## `checkout.failed`

It fires on **a decline as well as an expiry**. A caller whose card is declined and who then hangs
up is the case your server most needs to hear about, so it is an event, not something you discover
by polling.

```jsonc
"data": {
  "checkout_session_id": "cs_test_x9f2",
  "charge_id": "chg_5m1p",             // null when the session expired with no attempt
  "reason": "declined",                // "declined" | "expired"
  "amount_cents": 1900,
  "currency": "USD",
  "merchant_id": "tonys-pizza",
  "order_id": "ord_7f21",
  "platform_call_id": "call_abc123",
  "wallet": null,                      // the wallet a failed attempt came from; null on expiry
  "metadata": { "table": "12" },
  "last_payment_error": {              // null when the session merely expired
    "type": "processor_error",
    "code": "card_declined",
    "decline_code": "insufficient_funds",
    "advice_code": "try_again_later",
    "message": "Charge declined by the issuer.",
    "agent_message": "That card was declined for insufficient funds. Would you like to try a different card?",
    "agent_action": "offer_different_card",
    "doc_url": "https://docs.ringup.dev/api-reference/error-codes#card_declined",
    "charge": "chg_5m1p"
  }
}
```

`reason` tells the two cases apart:

- **`declined`.** A card was charged and the issuer said no. `charge_id` names the attempt, and
  `last_payment_error` says why.
- **`expired`.** The session lapsed unpaid. `charge_id` and `last_payment_error` are `null`:
  nothing was attempted, so there is no error to report.

`last_payment_error` is the **same error object** the `402` returned, so the parser you already
wrote for a synchronous decline handles the asynchronous one unchanged. See
[Errors](/api-reference/errors) for every field. It omits `request_id`: that identifies a request,
and an event is not one.

## `checkout.step_up_required`

Ringup screens the caller's number on every checkout. When it finds a positive risk signal, the
caller's saved card is **not** offered on that call: they are texted a payment link instead, which
proves possession of the phone. This event tells you that happened, so the answer to "why did my
caller get a link when they have a card on file" is in your logs before they ask.

It fires **once per session**, whichever signal found the risk, and only on a real signal. A
screening lookup that errors or cannot run is treated as neutral and produces no event, because a
gap on our side is not a fact about your caller.

```jsonc
"data": {
  "checkout_session_id": "cs_test_x9f2",
  "merchant_id": "tonys-pizza",
  "decision": "step_up",
  "reasons": ["ported_recently"],      // may carry more than one
  "attestation": "A",                  // the carrier's grade for the original call, or null
  "ported_recently": true,             // null when the lookup did not resolve
  "platform_call_id": "call_abc123",
  "metadata": { "ticket": "4821" }
}
```

`reasons` carries stable codes, not prose: `ported_recently` when the number changed hands inside
the last seven days, `attestation_C` or `attestation_F` when the carrier's signature on the
original call was poor or failed.

<Note>
Nothing here is spoken to the caller, and your agent should not repeat it. The payment line already
handles the moment gracefully: it offers the link warmly and never mentions checks or verification.
</Note>

## Charge statuses

A charge is in one of three states; the same values appear on the
[session](/concepts/checkout-session) and in the [charge](/concepts/charge) response:

- **`succeeded`**: the charge settled. This is the only status that means money moved.
- **`pending`**: not settled. The processor has not confirmed an outcome, and the payment may or
  may not have gone through, so never announce it either way.
- **`failed`**: the charge was declined or errored; nothing was charged.

## Getting it right

Three rules cover almost every webhook bug:

1. **Verify the signature.** Each request carries a `Ringup-Signature` header, an HMAC of the raw
   body plus the `Ringup-Timestamp`. Recompute it with your endpoint's signing secret and reject a
   mismatch or an old timestamp, so nobody can forge an event.
2. **Dedupe on `event_id`.** Delivery is at-least-once: Ringup retries on any non-2xx response, so
   an event can arrive more than once. Treat a repeated `event_id` as a no-op.
3. **Acknowledge fast.** Return `2xx` immediately and do your work asynchronously. Ringup retries
   with backoff and parks a persistently failing endpoint after several attempts.

<Note>
**Signature scheme.** `Ringup-Signature` is an HMAC-SHA256 over the timestamp and the raw request
body, signed with your endpoint's secret, sent as `v1=<signature>`. The secret is returned once,
in the registration response.
</Note>
